# CI/CD

<Term id="ci">CI</Term> คือระบบตรวจงานอัตโนมัติที่ทำงานทุกครั้งที่มีคนเปิด Pull Request หรือ push โค้ด มันตรวจว่าโค้ดใหม่ไม่ทำให้ของเดิมพัง **ก่อน** ที่ใครจะกด merge

<Simple>

เหมือนครูตรวจการบ้านก่อนรวมเล่ม ถ้ามีข้อผิด จะบอกเลยว่าผิดตรงไหน และจะไม่ยอมรวมเล่มจนกว่าจะแก้ ข้อดีคือคนตรวจเป็นหุ่นยนต์ จึงตรวจเหมือนกันทุกครั้ง ไม่เกรงใจ และไม่ลืม

ส่วน CD (Continuous Deployment) คือขั้นถัดไป: เอาของที่ตรวจผ่านแล้วขึ้นระบบจริงอัตโนมัติ

</Simple>

<Detail>

workflow อยู่ที่ `.github/workflows/ci.yml` ทำงานเมื่อ push หรือเปิด PR เข้า `main` และ `develop` และสั่งรันเองจากแท็บ Actions ได้ (`workflow_dispatch`) ถ้ามี push ใหม่บน branch เดิม รอบเก่าที่ยังค้างจะถูกยกเลิก (`concurrency`) ทุก job ประกาศ `permissions` ของตัวเอง และมี `timeout-minutes`

</Detail>

<Example>

CMAS มี job ทั้งหมด 12 ตัว ทำงานพร้อมกัน แล้วไปจบที่ job เดียวชื่อ `CI gate` ซึ่งเป็น check เดียวที่กฎของ `main` และ `develop` บังคับ ทั้ง PR ใช้เวลาประมาณ 70 วินาทีตอนวัดครั้งล่าสุด (ตัวเลขจาก ci-cd-plan.md)

</Example>

## เดินดู pipeline ทีละ job

ลองกดแต่ละ job ดู แล้วลองติ๊ก "แก้แค่เอกสาร" หรือกด "สมมติว่า job นี้ล้ม" เพื่อดูว่า `CI gate` เปลี่ยนอย่างไร

<PipelineExplorer />

## ก่อน push: รันตัวตรวจเองในเครื่องก่อน

<Simple>

รอ CI ตรวจแล้วเพิ่งรู้ว่าผิด เสียเวลารอหลายนาที ทีมจึงมีคำสั่งเดียวที่ตรวจชุดเดียวกับ CI ให้รันในเครื่องก่อนส่งงาน

</Simple>

<Detail>

```bash
npm run verify
```

คำสั่งนี้รันตามลำดับ `format:check` → `lint` → `typecheck` → `test` → `build` และหยุดตั้งแต่ขั้นแรกที่ล้ม ส่วนที่ `verify` **ไม่ได้ครอบคลุม** คือ job `db`, `e2e`, `docker` และชุดความปลอดภัย ซึ่งต้องรอ CI จริง ถ้าอยากเช็ก coverage แบบที่ CI บังคับ ให้รัน `npm run test:unit`

</Detail>

## CI แดงแล้วทำอย่างไร

<Steps>

1. เปิดแท็บ Checks ของ PR กด job ที่เป็นสีแดง แล้วอ่าน log หา error **บรรทัดแรก** (บรรทัดที่เหลือมักตามมาจากตัวแรก)
2. รันคำสั่งเดียวกันในเครื่อง คำสั่งของแต่ละ job อยู่ในตัวสำรวจด้านบน ตรง "รันซ้ำในเครื่อง"
3. แก้ แล้ว commit และ push CI จะรันใหม่เอง
4. ถ้ายังไม่ผ่าน กลับไปข้อ 1 ถ้าติดจริงๆ ถามในกลุ่มแชททีม

</Steps>

<Warning title="อย่ากด Re-run หวังให้ผ่านเอง">

ทีมไม่ใส่ retry อัตโนมัติ เพราะมันซ่อนปัญหา test ที่ล้มแบบสุ่ม (flaky) ถ้าเจอ test แบบนั้น ให้แจ้งทีมและแก้ภายใน 7 วัน ห้ามปิดหรือเลี่ยง `CI gate` และห้ามแก้ ruleset เพื่อให้ merge ได้

</Warning>

## หลักการ 6 ข้อที่ pipeline นี้ยึด

| หลักการ | แปลว่า |
| --- | --- |
| งานที่ไม่พึ่งกันรันพร้อมกัน | ผลออกเร็ว งานที่ถูกที่สุดจบก่อน |
| test ต้อง hermetic | CI ไม่แตะฐานข้อมูลจริงเลย ใช้ Postgres ชั่วคราวที่ตายพร้อม job |
| สิทธิ์น้อยที่สุด | ทุก job ได้เท่าที่จำเป็น (`permissions: {}` ที่ระดับ workflow แล้วเพิ่มทีละ job) |
| ไม่เชื่อโค้ดจาก fork | repo เป็น public: PR จาก fork ห้ามได้ secret และ PR เข้า `main` ต้องมาจาก repo นี้เท่านั้น |
| build ครั้งเดียว แล้วส่งต่อ | image ที่ทดสอบต้องเป็นตัวเดียวกับที่ขึ้นระบบจริง (ส่วนนี้เป็นแผน CD ที่ยังไม่ได้ทำ) |
| migration ต้องมีคนอนุมัติ | `prisma migrate deploy` กับฐานจริงรันได้เฉพาะ job deploy ห้าม `db push` |

## งานกลางคืน (Nightly)

บางการตรวจช้าเกินกว่าจะรันทุก PR หรือต้องเทียบกับข้อมูลที่เปลี่ยนไปตามเวลา จึงแยกไปรัน **ตี 2 เวลาไทย** ทุกคืนด้วย `nightly.yml` (กด Run workflow เองก็ได้)

| job | ตรวจอะไร |
| --- | --- |
| Secret scan, full history | สแกนหา secret ทั้งประวัติ ไม่ใช่แค่ commit ใหม่ |
| CodeQL (security-extended) | สแกนช่องโหว่แบบละเอียดกว่ารอบ PR |
| Image scan | สแกน image ที่ build ใหม่ รายงานช่องโหว่ระดับ HIGH ด้วย (ช่องโหว่ใหม่เกิดได้โดยโค้ดไม่เปลี่ยน) |
| xlsx is the latest SheetJS release | `xlsx` มาจาก CDN ซึ่งเครื่องมือทั่วไปมองไม่เห็นช่องโหว่ จึงเทียบเวอร์ชันกับหน้า release เอง |
| Mutation test (server src/lib) | ทดสอบว่า test จับความผิดของสูตรคำนวณได้จริง (Stryker) |
| Diagrams match the prototype | รายงานอย่างเดียว ไม่ทำให้ล้ม |
| Open an issue on failure | ถ้าข้างบนล้ม เปิดหรืออัปเดต issue ให้เอง |

## ถ้าจะตั้ง CI ในโปรเจกต์ใหม่ ทำตามลำดับนี้

<Simple>

อย่าพยายามทำทุกอย่างพร้อมกัน เริ่มจากสิ่งที่ปลอดภัยที่สุดก่อน แล้วค่อยเพิ่มของสะดวกทีหลัง

</Simple>

1. **ป้องกัน repo:** ต้องผ่าน PR, ต้องมี approval, ห้าม force push, เปิด secret scanning
2. **แยก job ให้ขนาน** แล้วรวมผลที่ gate เดียว
3. **สแกนความปลอดภัย:** dependency, secret, โค้ดเสี่ยง
4. **E2E smoke** เฉพาะเส้นทางหลักไม่กี่เส้น
5. **CD:** ส่งขึ้นระบบจริงเมื่อเลือกที่ deploy แล้ว
6. **Nightly** สำหรับของที่ช้าหรือเปลี่ยนตามเวลา

<Example title="สถานะของ CMAS (ตามเอกสาร 2026-10-24)">

ลำดับด้านบนคือ P1 ถึง P6 ของ CMAS ลงโค้ดแล้ว **P1 ป้องกัน, P2 ขนาน, P3 สแกน, P4 E2E, P6 Nightly** ส่วน **P5 CD เลื่อน** เพราะทีมยังไม่เลือกที่ deploy (Railway หรือ Fly.io) การตั้งค่าบน GitHub เอง (ruleset, secret scanning) ต้องให้ admin ของ organization ทำ แก้ในโค้ดแทนไม่ได้

</Example>
