# PR & Code Review

<Term id="pull-request">Pull Request</Term> คือคำขอให้รวมงานของคุณเข้ากองกลาง และ Code Review คือการที่เพื่อนอ่านงานก่อนรวม หน้านี้บอกว่าคนเปิด PR ต้องเตรียมอะไร และคนรีวิวต้องดูอะไร

<Simple>

การรีวิวไม่ใช่การจับผิด แต่คือ **สายตาคู่ที่สอง** คนเขียนมักมองไม่เห็นข้อผิดพลาดของตัวเอง ทีมมีกันสามคน จึงตกลงว่าทุกงานต้องมีเพื่อนอย่างน้อยหนึ่งคนอ่านและกดอนุมัติ ก่อนรวมเข้ากองกลาง ส่วนเรื่องที่หุ่นยนต์ตรวจแทนได้ (รูปแบบโค้ด ชนิดข้อมูล test) ปล่อยให้ CI ตรวจ คนรีวิวจะได้โฟกัสเรื่องที่ต้องใช้คนคิด

</Simple>

<Detail>

กฎที่ระบบบังคับ: `main` และ `develop` ต้องผ่าน PR, ต้องมี approval 1 คน (เจ้าของ PR approve เองไม่ได้), ต้องผ่าน check `CI gate`, ห้าม force push และห้ามลบ branch ไฟล์ที่อยู่ใน `.github/CODEOWNERS` ต้องให้เจ้าของไฟล์อนุมัติ merge ใช้ merge commit เสมอ ไม่ใช่ squash หรือ rebase

</Detail>

## เส้นทางของ PR หนึ่งใบ

<Steps>

1. **ผู้เขียน** ตรวจงานตัวเองในเครื่อง (`npm run verify`) merge `develop` ล่าสุดเข้า branch ตัวเอง แล้วเปิด PR เข้า `develop`
2. **ผู้เขียน** แจ้งในกลุ่มแชทว่าเปิด PR แล้ว
3. **CI** รันอัตโนมัติ ต้องผ่านที่ `CI gate` (ดูหน้า [CI/CD](/ci))
4. **ผู้รีวิว** (เพื่อนคนใดคนหนึ่งในสองคนที่เหลือ) อ่าน ถามหรือขอแก้ แล้วกด Approve
5. merge ด้วย **merge commit** แล้ว **ผู้เขียนลบ branch** ที่ใช้เสร็จแล้ว

</Steps>

## ไฟล์ที่ต้องให้เจ้าของดู

<Simple>

ไฟล์บางกลุ่มถ้าพลาดแล้วเสียหายหนักกว่าบั๊กทั่วไป เช่น ทำให้ความลับรั่วหรือข้อมูลของรายวิชาหนึ่งไปโผล่ให้อีกรายวิชา PR ที่แตะไฟล์เหล่านี้จึงต้องได้รับการอนุมัติจากเจ้าของไฟล์ ไม่ใช่เพื่อนคนใดก็ได้

</Simple>

<Example title="ไฟล์ใน CODEOWNERS ของ CMAS">

| ที่อยู่ | เหตุผล |
| --- | --- |
| `.github/` | แก้ workflow อาจทำให้ความลับรั่ว หรือข้ามการตรวจทุกอย่างได้ |
| `database/migrations/` และ `database/schema.prisma` | Prisma บันทึกชื่อ migration ไว้ในฐานข้อมูล และบางไฟล์เป็น SQL ที่เขียนมือ |
| `app/server/src/modules/authorization/` และ `middlewares/` | ขอบเขตข้อมูลรายวิชา และด่านตรวจสิทธิ์ |
| `app/server/src/modules/auth/` และ `lib/jwt.ts` | เส้นทางการล็อกอินและการออก token |
| `Dockerfile.prod` (client และ server) และ `docker-compose.prod.yml` | สิ่งที่ขึ้นระบบจริง |

</Example>

<Warning title="แก้ช่องโหว่ด่วนก็ต้องมีคนรีวิว">

โค้ดที่แก้ช่องโหว่ห้าม deploy โดยไม่ผ่านการรีวิวจากอีกหนึ่งคน แม้จะเร่งด่วน ให้ใช้ขั้นตอน hotfix ในหน้า [Git](/git) และแจ้งทีมทันทีว่ามีของด่านรอรีวิว

</Warning>

## อ่านต่อ

- ขั้นตอนเปิด PR และกติกา branch: หน้า [Git](/git)
- สิ่งที่ CI ตรวจให้อัตโนมัติ: หน้า [CI/CD](/ci)
- กฎโค้ดที่ผู้รีวิวใช้เทียบ: [โครงสร้างโค้ด & กฎ](/code) และ [Security](/security)
