# สถาปัตยกรรมระบบ

หน้านี้พาดูภาพรวมว่าระบบประกอบจากอะไร ใครคุยกับใคร ผ่านช่องทางอะไร (protocol) และแต่ละส่วนใช้เครื่องมืออะไร ตัวแผนภาพมาจากไฟล์ `docs/diagrams/architecture/CMAS-Architecture-Overview.drawio` ซึ่งมี 4 หน้า ผมแปลงเป็น 4 ส่วนที่กดดูได้ด้านล่าง

<Simple>

ลองนึกถึงการสั่งอาหารผ่านแอป: **หน้าจอแอป** คือหน้าร้าน **server** คือห้องครัวที่ตรวจว่าคุณเป็นใครและมีสิทธิ์สั่งไหม **ฐานข้อมูล** คือคลังวัตถุดิบ และ **Google** คือคนตรวจบัตรประชาชนให้ ระหว่างแต่ละจุดมี "ช่องทางขนส่ง" (protocol) ที่ต่างกัน เช่น จดหมายปิดผนึก (HTTPS) หรือท่อลับ (TCP + TLS) หน้านี้บอกว่าแต่ละช่องทางคืออะไร

</Simple>

<Detail>

ระบบเป็น single-tenant: **React → Fastify → PostgreSQL** โดยมีขอบเขตข้อมูลเดียวคือรายวิชา ฝั่ง client กับ server คุยกันผ่าน REST/JSON บน HTTPS แนบ JWT ส่วน server กับฐานข้อมูลคุยผ่าน Prisma (SQL บน TCP + TLS) และการเข้าสู่ระบบใช้ Google (OpenID Connect) เท่านั้น

</Detail>

<Warning title="แผนภาพนี้นำหน้าโค้ดอยู่บางส่วน">

ผมเทียบแผนภาพกับโค้ดบน branch `develop` (2026-11-08) และติดป้าย "ตามแผน" ไว้กับสิ่งที่วาดไว้แต่ยังไม่พบในโค้ด ได้แก่ SSE (อัปเดตสด), cookie ของ refresh token, apiClient ที่ refresh token เอง, ตาราง `RefreshToken`, migration 0008–0009 (RLS) และ modules `courses` `clos` `activities` `scores` `students` `dashboard` ส่วนข้อมูลด้าน infrastructure (Session pooler, พอร์ต) ยกมาจากแผนภาพ ผมตรวจจากโค้ดไม่ได้

</Warning>

## 3. ล็อกอินด้วย Google

<Simple>

ผู้ใช้ไม่ต้องตั้งรหัสผ่านกับระบบเรา แต่ให้ Google ยืนยันตัวตนแทน เหมือนไปงานที่ต้องโชว์บัตร: Google ตรวจบัตรแล้วออก "ใบรับรอง" ให้ เรานำใบรับรองนั้นไปให้ server ตรวจอีกที ถ้าผ่านก็ได้บัตรผ่านของระบบเราไปใช้งาน

</Simple>

เลือกสถานการณ์ แล้วกด "ถัดไป" ทีละขั้น ดูว่า protocol ไหนทำหน้าที่ตรงไหน

<LoginFlow />

<Example title="อีเมลของคนนอกโดเมนสถาบัน">

อีเมลใน `ADMIN_EMAILS` ได้เป็น ADMIN ตอนล็อกอินครั้งแรก อีเมลที่ลงท้ายด้วย `INSTITUTION_EMAIL_DOMAIN` ได้เป็น INSTRUCTOR ทันที ส่วนอีเมลอื่นจะได้บัญชีสถานะรออนุมัติ (PENDING) จนกว่า ADMIN จะกดอนุมัติ นี่คือสถานการณ์ "บัญชียังไม่ได้รับอนุมัติ" ด้านบน

</Example>

## 4. คำขอหนึ่งครั้งเดินทางอย่างไร

ตามคำขอ "ADMIN อนุมัติผู้ใช้" ตั้งแต่กดปุ่มจนข้อมูลเปลี่ยนในฐานข้อมูล และเห็นว่าแต่ละขั้นใช้เครื่องมืออะไร

<RequestWalk />

<Detail>

แผนภาพต้นฉบับยังเรียกขั้นตรวจสิทธิ์ว่า `rbac('ADMIN')` แต่โค้ดตอนนี้ใช้ `access.middleware` ที่อ่าน `config: { access: { cap: "user.manage" } }` ของ route แล้วเทียบ role กับ capability หน้านี้เดินตามโค้ด และเลข ①–⑩ ในแผนภาพต้นฉบับไม่ตรงกับเลขขั้นด้านบน

</Detail>

## ช่องทาง (protocol) ที่ใช้ในระบบ

| ช่องทาง | อยู่ระหว่าง | เปรียบเทียบง่ายๆ | สถานะ |
| --- | --- | --- | --- |
| **HTTPS** | ผู้ใช้ ↔ หน้าเว็บ, หน้าเว็บ ↔ server, server ↔ Google | จดหมายใส่ซองปิดผนึก | ใช้อยู่ |
| **REST API (JSON)** | หน้าเว็บ ↔ server | แบบฟอร์มสั่งของที่ทุกคนใช้รูปแบบเดียวกัน | ใช้อยู่ |
| **JWT (Bearer token)** | แนบกับทุกคำขอ | บัตรผ่านที่มีวันหมดอายุ | ใช้อยู่ (access token 15 นาที) |
| **OpenID Connect** | Google ↔ เบราว์เซอร์ ↔ server | บัตรประชาชนที่ Google ตรวจให้ | ใช้อยู่ |
| **TCP + TLS** | server ↔ ฐานข้อมูล | ท่อลับที่เข้ารหัส | ใช้อยู่ |
| **SQL (ผ่าน Prisma)** | server ↔ ฐานข้อมูล | ภาษาที่ใช้สั่งคลัง | ใช้อยู่ |
| **HTTP cookie** | server ↔ เบราว์เซอร์ | ลิ้นชักล็อกในเบราว์เซอร์ที่เก็บบัตรสำรอง | ตามแผน |
| **Server-Sent Events** | server → หน้าเว็บ | คนมาเคาะประตูบอกข่าว | ตามแผน |
